# 구현 파이프라인 — 무엇을, 왜 그렇게 했는가

현행 구현 기준 · 실행 로그에서 확인한 수치만 적었다
코드 실행 방법은 [`demo/README.md`](../demo/README.md) 를 본다. 이 문서는 **설계 근거**를 다룬다.

---

## 0. 이 시스템이 답하는 것

농장주가 아침에 묻는다. **"오늘 액비 뿌려도 될까? 안 되면 언제?"**

시스템은 앞으로 3~7일의 매 시각에 위험 점수를 매기고, 작업 시작 후 6시간을 묶어
가장 안전한 창과 가장 위험한 창을 돌려준다. 여기에 저감 조치 조언이 붙는다.

**"악취가 언제 심한가"를 맞히는 게 아니다.** 우리가 가진 정답지는 민원 접수 기록이고,
그건 냄새의 세기가 아니라 **사람이 신고할 만큼 불쾌했는가**의 기록이다.
그래서 결과물의 이름도 "악취 위험도"가 아니라 **"민원 위험도"** 다.

## 1. 두 모델의 역할 분담

이 프로젝트에서 가장 자주 오해받는 지점이다.

```
   XGBoost  ─ 언제 민원이 나는가   ─ 민원 이력 × 기상 실측으로 학습
   플룸     ─ 어디로 냄새가 가는가 ─ 바람 + 농가 좌표로 계산 (학습 없음)
```

**둘을 곱하지 않는다.** 바람과 주야간은 이미 XGBoost 피처 안에 들어 있다.
여기에 플룸 점수를 곱하면 같은 물리량을 두 번 세는 것이 된다.

그래서 플룸에는 **선택권만** 준다. XGBoost 가 두 수용점 유형(농촌근거리·시가지원거리)에
각각 점수를 매겨 놓으면, 플룸은 "지금 바람으로는 이 농가의 냄새가 저쪽으로 간다" 를 보고
**둘 중 어느 점수를 볼지 고른다.** 점수 자체는 건드리지 않는다.

물리 정보가 들어가는 자리는 딱 둘까지다.

```
   ① 피처 — 풍상측 노출     수용점 기준 "어디서 오나"   학습 단계   ✅ 사용
   ② 조합 — 유형 선택       발원 기준   "어디로 가나"   서빙 단계   ✅ 사용
   ③ 등급 보정 (BUMP)      최종 등급을 가감            추천 단계   ❌ 영구 OFF
```

①과 ②는 방향도 단계도 반대라 이중 계산이 아니다. ③까지 켜면 삼중이 된다.
`PLUME_GRADE_BUMP = False` 는 영구 설정이다.

## 2. 격자를 다시 정의한 이야기 — 이 프로젝트의 분기점

### 원래는 3시간 블록이었다

하루를 3시간씩 8칸으로 나누고, 각 칸에 "민원이 있었나"를 붙였다.
근거는 "신고 시각엔 냄새 맡고 신고하기까지의 지연이 섞여 있으니 넓은 창이 노이즈를 흡수한다" 였다.

### 측정해 보니 반대였다

```
   냄새 도달 시간 중앙값          32분
   3시간 창 안에서 풍향이 바뀌는 비율   58.6%
```

3시간이면 바람이 절반 넘게 방향을 바꾼다. **블록 평균 풍향은 실제로 분 적 없는 바람이다.**
넓은 창은 노이즈를 흡수한 게 아니라 신호를 뭉갠 것이었다.

### 그리고 익산은 하나가 아니었다

왕궁면 흥암리와 시가지의 시간별 민원 상관은 **0.014** — 사실상 무관하다.
도달 시간도 5~17분 대 50~90분으로 지배하는 물리가 다르다.
한 덩어리로 학습하면 서로를 노이즈로 만든다.

### 그래서 격자를 바꿨다

```
   이전   (날짜, 3시간 블록)          19,208행 · 양성률 13.2%
   현행   (1시간, 수용점 유형)        115,352행 · 양성률 2.36%
```

한 행이 "언제"만이 아니라 **"언제 + 누구에게"** 를 뜻하게 됐다.
양성률이 13.2% → 2.36% 로 떨어진 건 성능 하락이 아니라 **문제가 정확해진 결과**다.
칸이 6배 잘게 쪼개졌으니 한 칸당 민원 밀도가 낮아지는 게 당연하다.
이전 수치와 직접 비교하면 안 된다.

수용점 유형은 2개다.

| 유형 | 정체 | 중심 좌표 산출 | 양성 |
| --- | --- | --- | --- |
| 농촌근거리 | 축사에 가까운 농촌 마을 | 민원 1,259건의 중앙값 | 945 / 57,676 (1.64%) |
| 시가지원거리 | 축사에서 먼 시가지 | 민원 3,484건의 중앙값 | 1,780 / 57,676 (3.09%) |

유형을 특정할 수 없는 민원 820건(14.7%)은 학습에서 제외했다.

## 3. 단계별 구현

각 단계는 **입력 → 처리 → 출력 → 왜 이렇게 했나** 순으로 적는다.

### 단계 1 — 민원·기상 정제 · `preprocess/clean_data.py`

**입력** 민원 xlsx 13,039행 (2020.01~2026.07) · 기상 CSV 57,695행

**처리**
```
   ① 익산시 필터          완주군이 8.3% 섞여 있다 → 익산 5,654건
   ② 가축분뇨(101) 필터    악취 종류가 여럿인데 우리 대상은 분뇨뿐
   ③ 중복 제거            좌표 4자리 반올림 + 10분 이내 재신고 → 1건으로
   ④ 기상 결측 보간        3시간 이내만 선형보간
```

**출력** `complaints_clean.parquet` 12,422행 (필터는 플래그로 보존, 중복만 실제 제거)

**왜**
- **풍향은 sin/cos 로 바꾼다.** 359°와 1°는 2° 차이인데 숫자로는 358 만큼 멀다.
  각도를 그대로 넣으면 모델이 정북 근처를 정반대로 학습한다.
- **강수량 빈칸은 결측이 아니라 0 이다.** 기상청 표기 관행이다.
  결측으로 처리해 보간하면 비가 안 온 날에 비를 만들어 낸다.
- 필터링한 행을 **버리지 않고 플래그로 남긴다.** 나중에 "완주군 빼면 어떻게 되나"를
  다시 물을 때 원본을 다시 읽지 않아도 된다.

### 단계 2 — 김제 농가 재지오코딩 · `preprocess/geocode_gimje.py`

이 단계는 원래 계획에 없었다. **검증 중에 발견한 것 때문에 생겼다.**

풍상측 15km 안의 농가를 세어 봤더니, **민원의 26.2% 가 "익산 농가 0곳, 김제 농가만 있음"** 이었다.
익산 농가만 보고 있으면 민원 넷 중 하나는 발원을 못 찾는다.

문제는 김제 공공데이터의 번지가 `***` 로 마스킹돼 있다는 것이다. 상호명 매칭으로는
1,511곳 중 **12.2%** 만 좌표를 얻었다.

**해법** — 번지는 가려졌지만 **리(里) 이름은 살아 있다.** 같은 리에서 실좌표를 얻은
농가들의 좌표 중앙값으로 나머지를 채웠다.

```
   실좌표[A]      184곳     상호명 매칭 성공
   리중앙값[B]     975곳     같은 리의 실좌표 중앙값
   읍면중앙값[C]   290곳     리 단위로도 못 찾아 읍면 중앙값
   없음            62곳
   ─────────────────────
   좌표 확보율   12.2% → 95.9%
```

근거 등급을 좌표마다 붙여 뒀다. **[C] 는 오차가 크다는 뜻이고, 이 딱지가 있어야
나중에 결과가 이상할 때 어디를 의심할지 알 수 있다.**

리 중앙값의 위치 오차는 1~2km 로 추정된다. 이 숫자가 뒤의 플룸 설계를 결정한다.

### 단계 3 — 격자와 정답 라벨 · `preprocess/build_grid.py`

**출력** `label_table.parquet` 115,352행

```
   한 행 = (1시간, 수용점 유형)      57,696시각 × 2 유형 = 115,392
                                    기상 결측 40행 제외 → 115,352
   정답 y_bin  = 그 시각 그 유형에 민원이 났는가 (0/1)
   가중치 y_sev = 악취 강도 1~5
```

**왜 강도를 가중치로 쓰나** — 강도 5짜리 민원과 강도 1짜리 민원을 같은 1로 세면,
"참기 힘든 악취"와 "좀 나는 것 같다"가 동급이 된다. 정답은 0/1 로 두되
**학습할 때의 중요도만** 강도에 비례시켰다.

### 단계 4 — 풍상측 노출 · `preprocess/spatial_features.py`

이 파이프라인에서 **물리를 피처로 넣는 유일한 자리**다.

각 시각·각 수용점에서 **바람이 불어오는 쪽(풍상측) ±30°, 15km 부채꼴 안에 농가가 몇 곳인지** 센다.

```
   up_ik_pig / up_ik_cattle / up_ik_poultry      익산 농가 — 돼지 / 소 / 가금
   up_gj_pig / up_gj_cattle / up_gj_poultry      김제 농가 — 돼지 / 소 / 가금
   up_nearest_km                                 가장 가까운 풍상측 농가까지 거리
```

**왜 축종을 나누나** — 민원 라벨이 "가축 분뇨 냄새(닭·돼지·소)" 한 종류라 축종 구분이 없다.
그래서 대상도 전 축종이다. 다만 축종마다 배출 특성이 달라 **모델이 스스로 구분할 수 있게**
따로 세어 준다. 합쳐서 하나로 주면 그 정보가 사라진다.

**왜 익산과 김제를 나누나** — 단계 2 에서 본 26.2% 때문이다.
김제 발원은 우리가 손댈 수 없는 영역이라 **효과 상한선을 보여 주는 값**이기도 하다.

**이건 플룸이 아니다.** 부채꼴 안의 개수를 세는 순수 기하 계산이다.
확산 계수도, 안정도 등급도 쓰지 않는다.

같이 만드는 것이 **직전 1년 민원율** 3종이다.

```
   prior_rate_1y · prior_std_1y · prior_month
```

여기엔 함정이 하나 있다. 오늘의 민원율을 계산할 때 **오늘을 포함하면 정답을 미리 보는 것**이다.
`shift(1)` 로 하루 밀어낸 뒤 `rolling("365D")` 를 건다. 순서가 반대면 누수가 난다.

### 단계 5 — 시차·무풍 피처 · `preprocess/build_features.py`

1시간 격자가 되면서 비로소 가능해진 피처들이다. 3시간 블록에서는 만들 수 없었다.

```
   ws_lag1 · ws_lag2              1시간 전 · 2시간 전 풍속
   wd_sin_lag1 · wd_cos_lag1      1시간 전 풍향
   calm_streak                    무풍이 몇 시간째 이어지는가
```

**왜 시차가 필요한가** — 냄새 도달 중앙값이 32분이다. **지금 신고된 냄새를 실어 온 바람은
지금 바람이 아니라 한 시간 전 바람이다.**

**왜 무풍 연속인가** — 바람이 없으면 냄새가 흩어지지 않고 고인다.
한 시간 무풍과 다섯 시간째 무풍은 전혀 다른 상황인데, 순간 풍속만 보면 둘 다 "0.3 m/s" 다.

최종 28개 피처.

| 묶음 | 개수 | 피처 |
| --- | --- | --- |
| 기상 | 6 | temp · humid · ws · wd_sin · wd_cos · rain |
| 야간 | 3 | night · night_ws · night_humid |
| 시각 | 4 | hour · month_sin · month_cos · dow |
| 시차·무풍 | 5 | ws_lag1 · ws_lag2 · wd_sin_lag1 · wd_cos_lag1 · calm_streak |
| 공간 | 7 | up_ik_* · up_gj_* · up_nearest_km |
| 과거율 | 3 | prior_rate_1y · prior_std_1y · prior_month |

**기상 6개는 전부 기상청 단기예보가 주는 변수와 1:1 대응한다.**
TMP·REH·WSD·VEC·PTY 다. 이게 절대규칙이다 — 예보에 없는 변수를 넣으면
학습은 되는데 서빙이 안 되는 모델이 만들어진다.

### 단계 6 — 학습 · `model/train_model.py`

**유형별로 따로 학습한다.** 왕궁과 시가지는 지배 물리가 달라 한 모델로 묶으면 서로를 방해한다.

```
   분할   train ≤ 2023   35,062행
          valid   2024    8,784행
          test    2025    8,743행
```

**왜 시간순 분할인가** — 무작위 분할은 계절 누수를 만든다.
같은 해 7월 데이터가 학습과 평가에 동시에 들어가면 "7월엔 민원이 많다"를
외운 것만으로 점수가 오른다. 미래를 예측하는 시스템이니 **평가도 미래로** 해야 한다.

**불균형 처리 2중**
```
   scale_pos_weight    농촌 140.4 · 시가지 26.5   (음성/양성 비율)
   sample_weight       악취 강도 1~5
```

**월별 등급컷 12개** — 컷을 하나로 잡으면 여름엔 전부 위험, 겨울엔 전부 낮음이 된다.
계절 드리프트를 흡수하려고 월마다 따로 잡았다.

```
   농촌근거리 주의컷   1월 0.659  →  8~10월 0.797
```

### 단계 7 — 매일 서빙 · `serving/daily_scoring.py`

**입력** 기상청 단기예보 API (D+1~3, 1시간 단위, 약 81시점)

여기에 **함정이 하나** 있었다.

`ws_lag1` 과 `calm_streak` 은 과거 값이 있어야 계산된다. 예보 첫 시각에는 과거가 없으니
0 에서 시작하는데, **학습 때는 그런 행이 없었다.** 서빙 입력이 학습 분포 밖으로 나간다.

**해법** — 예보 앞에 **관측 마지막 48시간을 이어 붙인다.** 시차와 무풍 연속이
실제 값에서 출발한다.

```
   관측 꼬리 48시각  +  단기예보 81시각  =  162행
   중기예보 192행 (D+4~7, 일 단위 → reduced 모델 7피처)
   ────────────────────────────────────
   누적 354행 → SQLite
```

**학습과 같은 함수를 쓴다.** `spatial_features.run_serving()` 은 학습용 `run()` 과
같은 코드에 `save=False` 만 다르다. 서빙용 계산을 따로 짜면 반드시 어긋난다.

> **실제로 어긋났던 적이 있다.** 그룹 중심 좌표가 학습 프로세스의 메모리에만 있어서
> 서빙은 설정 파일의 기본값을 썼다. 시가지 중심이 약 0.9km 어긋난 채로 돌고 있었고,
> 아무 에러도 안 났다. 지금은 `data/group_center.json` 으로 파일에 떨궈 양쪽이 같은 값을 읽는다.

**저장** — SQLite `risk_hourly`, PK 는 `(date, hour, grp)` 다.
`grp` 가 빠지면 두 유형 중 하나가 다른 하나를 덮어쓴다.

### 단계 8 — 추천 · `advisor/recommend.py`

순서가 곧 설계다.

```
   ① 법령 하드필터  [미구현]     법이 먼저 자른다. 모델은 법을 모른다.
            ↓
   ② ML 랭킹                    6시간 창 감쇠 가중평균
            ↓                   [0.30 0.22 0.17 0.13 0.10 0.08]
   ③ 플룸 — 유형 선택만          곱하지 않는다
            ↓
   ④ 조합 × 작업가중 × 저장경과
            ↓
   ⑤ 등급 — 두 층
```

**왜 시점이 아니라 창인가** — 냄새는 뿌린 순간이 아니라 이후 몇 시간에 걸쳐 퍼진다.
작업 시작 후 6시간의 위험도를 감쇠 가중평균한다. 초반 시간에 더 큰 가중치가 간다.
6시간을 다 덮지 못하는 시각은 후보에서 뺀다.

**왜 법령이 ML 보다 먼저인가** — 반대로 하면 **법적으로 뿌리면 안 되는 시각이
A등급으로 추천된다.** 강우·결빙·부숙도·질소상한은 모델이 모르는 조건이다.
아직 미구현이며 남은 작업 1순위다.

**플룸의 3km 경계**

```
   ≤ 3km   플룸 유효 반각을 쓴다 (Briggs Open-Country σy · Pasquill 안정도)
   > 3km   고정 섹터 ±30° 로 대체
```

**왜 자르나** — 15km 지점에서 F등급(가장 안정) 플룸의 반폭은 **814m** 다.
그런데 김제 농가 좌표의 오차가 **1~2km** 다. 좌표 오차가 플룸 폭보다 크면
정밀한 계산은 정밀한 착각일 뿐이다. 오차가 폭을 넘어서는 지점에서 계산을 포기하고
넉넉한 섹터로 바꾼다.

**등급이 두 층인 이유**

```
   위험 / 주의 / 낮음     월별 컷 기준       "이 시각의 절대 위험 수준"
   A / B / C            후보 집합 내 순위   "지금 고를 수 있는 것 중 상대 순위"
```

농장주에게 필요한 건 **"이번 주에 그나마 나은 때가 언제냐"** 다.
한 주가 통째로 나쁘면 절대 등급은 전부 "위험"이지만, 그중에도 덜 나쁜 시각은 있다.
A/B/C 는 후보 안에서 하위 20/30/50% 로 매긴다.

### 단계 9 — 설명 계층 · 판단하지 않는다

```
   legacy/emission.py    "주입식 57% 감소" · "즉시 경운 38% 감소"
   rag/                  법령 조문 근거 검색
   agents/               LLM 서술
```

**이 층은 등급을 바꾸지 않는다.** RAG 가 엉뚱한 조문을 물어 와도, LLM 이 이상한 문장을
써도 추천 시각과 등급은 그대로다. 판단은 코드가, 설명은 LLM 이 한다.

**배출량 kg 절대값은 출력하지 않는다.** 매뉴얼 실측 기반 계수라 상대 감소율
("주입식으로 바꾸면 57% 감소")은 말할 수 있지만, "오늘 12.4kg 나옵니다" 같은
절대값은 근거가 없다. 감소율만 말한다.

## 4. 성능

**test 는 2025년, 학습에 한 번도 안 쓴 구간이다.**

| 유형 | 분할 | ROC-AUC | PR-AUC | lift | 상위20% 재현율 | A등급 민원율 |
| --- | --- | --- | --- | --- | --- | --- |
| 시가지원거리 | valid 2024 | 0.884 | 0.195 | 10.5배 | 81.1% | 평균의 1/16.4 |
| **시가지원거리** | **test 2025** | **0.899** | **0.221** | **7.7배** | **85.3%** | **평균의 1/16.7** |
| 농촌근거리 | valid 2024 | 0.785 | 0.141 | 3.4배 | 62.0% | 평균의 1/12.0 |
| 농촌근거리 | test 2025 | 0.724 | 0.074 | 2.5배 | 48.8% | 평균의 1/7.3 |

중기예보용 reduced 모델(7피처, 바람 없음): 시가지 test PR-AUC 0.185(lift 6.4배) / 농촌 0.082(2.8배).

> 위 값은 전부 `python run_train.py` 가 `out/training_results.json` 에 기록한다.
> 문서의 숫자와 파일의 숫자가 다르면 **파일이 옳다.**
> `lift` 는 PR-AUC ÷ 양성률, `a_grade_ratio` 는 전체 민원율 ÷ 하위20% 시각 민원율이다.

### PR-AUC 0.221 이 좋은 건가

양성률이 2.9% 인 문제다. **아무렇게나 찍으면 PR-AUC 가 0.029 나온다.**
0.221 은 그 **7.7배**다.

실무적으로 읽으면 이렇다.
```
   상위 20% 시각만 피하면    실제 민원의 85.3% 를 피한다
   A등급 시각의 민원 발생률   전체 평균의 1/16.7
```

### 농촌근거리가 왜 낮은지는 파악돼 있다

왕궁면 흥암리 민원이 **2020~2023 통틀어 1건**이었다가 **2024년에 517건**으로 뛰었다.
학습 구간(≤2023)과 평가 구간(2025)의 지역 구성이 아예 다르다.
모델이 못 배운 게 아니라 **배울 데이터가 그 구간에 없었다.**

원인이 앱 보급인지, 지역명 표기 변경인지, 실제 사건인지는 확인이 필요하다.
이걸 모르는 채로 농촌 모델 성능을 개선하려 드는 건 방향이 틀렸다.

## 5. 검증에서 기각된 주장들

**실패가 아니라, 심사위원이 묻기 전에 우리가 먼저 재 본 결과다.**

| 처음 주장 | 시험 결과 | 지금 주장 |
| --- | --- | --- |
| "기상으로 민원을 예측한다" | 성능의 바닥은 달력(계절+시간대)이었다 | "달력 위에 기상이 증분을 얹는다" |
| "특이한 날씨를 잡아낸다" | 증분은 오히려 평범한 날에 컸다 | "기상의 역할은 극단 탐지가 아니라 상시 미세 보정" |
| "플룸이 냄새 방향을 맞힌다" | 기준 3개 중 1개만 통과 | "등급엔 안 쓰고 대상 선택에만" |
| "공간 피처가 성능을 크게 올린다" | 단일 시드 비교는 노이즈였다 | 5시드로 재측정 후 재서술 |
| "민원을 줄여준다" | 농가 행동↔민원 데이터가 세상에 없다 | "상대적으로 위험한 시각 회피를 돕는다" |

### 특히 조심해야 하는 것 — grouped CV 의 PR-AUC 1.0000

지역을 통째로 빼고 평가하는 grouped CV 에서 **4개 폴드 전부 PR-AUC 1.0000** 이 나온다.

**이건 완벽한 성능이 아니라 지표가 무의미해진 것이다.**
`region` 컬럼이 민원이 있는 행에만 존재해서, 지역으로 자른 시험지가 **전부 양성**이 된다.
양성률 1.0 인 시험지에서 PR-AUC 는 항상 1 이다.

지역 격자 트랙(`run_train_region.py`)은 모든 격자에 지역을 부여해 이 문제를 피한다.
거기서는 lift 17.6~19.1배 같은 정상적인 값이 나온다.

**발표에서 이 1.0000 을 성능으로 인용하면 안 된다.**

## 부록 — 기상 관측소를 둘 쓰는 이유

| 용도 | 관측소 | 이유 |
| --- | --- | --- |
| ML 학습 피처 | 전주 ASOS (146) | 무풍 7.1% · 결측 34건 |
| 플룸 계산 | 익산 AWS (702) | 익산 현지 바람 |

익산 AWS 는 전주와 **25.8% 의 시각에서 풍향이 90° 이상 어긋난다.** 현지 바람이니
익산을 쓰는 게 맞아 보이지만, 데이터 품질이 나쁘다 — **무풍 16.5%, 결측 408건.**
무풍으로 기록된 시각은 풍향이 의미를 잃어 시차 피처가 통째로 망가진다.

그래서 역할을 나눴다. **학습은 품질이 좋은 전주, 플룸의 순간 방향 판정은 현지인 익산.**
이건 타협이며, 익산 AWS 품질이 개선되면 재검토할 일이다.
