# 악취 민원 예측 프로젝트 — 구현 파이프라인 완전 설명서

팀 배포용 · 2026\-08\-10 기준 실제 구현 내용 반영 · "프로젝트 데이터" 폴더와 이 문서만으로 전체를 이해할 수 있게 작성됨

## 0\. 이 문서를 읽는 법

같이 배포된 **"프로젝트 데이터" 폴더**가 이 프로젝트의 모든 원료다. 이 문서는 (1) 그 폴더에 뭐가 들어있고 (2) 각 파일이 파이프라인 어디에 들어가서 (3) 무엇이 되어 나오는지를 순서대로 설명한다. 코드(demo 폴더)는 별도로 공유되며, 이 문서의 각 단계에 해당 스크립트 이름을 적어뒀다.

**프로젝트 한 줄:** 익산시의 실제 악취 민원 6년치와 기상 데이터의 관계를 학습해서, 기상 예보만으로 "이번 주 언제가 민원 위험이 높은지"를 예측하고 양돈농가에 안전한 작업 시간대를 추천하는 시스템.

**설계의 제1원칙 — 예측은 역할이 다른 두 모듈로 분리된다:**

| 모듈 | 답하는 질문 | 재료 | 현재 상태 |
| --- | --- | --- | --- |
| 통계 모델 (XGBoost) | **언제** 민원이 나는가 | 민원 이력 × 기상 실측 | ✅ 검증 통과 (랜덤 대비 2.3배) |
| 물리 모델 (플룸) | **어디로** 냄새가 가는가 | 바람 \+ 농가·주택 좌표 | ⚠️ 참고 정보로만 사용 (검증 기준 근소 미달로 등급 반영 OFF) |

두 모듈은 절대 곱하지 않는다(바람·주야간 변수가 겹쳐 이중 계산됨). 캘린더 등급은 통계 모델 단독, 주민 알림 대상은 플룸\+부채꼴 합집합.

## 0\.5 프로젝트 오버뷰 — 처음 아이디어가 어떻게 지금의 모습이 됐나

이 절만 읽으면 "뭐가 기각됐다는데 그래서 지금 프로젝트가 뭔데?"가 풀린다. 프로젝트의 주제는 그대로이고, 검증을 거치며 **주장이 구체적인 수치로 다듬어진 것**이다.

**시작 (8/8 회의):** "기상 조건(풍향·풍속·온도·습도)과 축산 악취 민원 발생 시점의 상관관계를 분석해, 민원 위험도를 사전에 예측하고 양돈농가의 작업 시간대를 추천하는 AI 모델." — 이 한 줄은 지금도 유효하다. 아래는 그 한 줄이 구체화되며 다듬어진 과정이다.

**전환 1 — "NH₃로 예측"을 버리고 "예보 가능한 것만"으로.** 초기엔 공기 중 암모니아 농도를 입력으로 쓰는 구상이 있었으나, NH₃는 **예보가 존재하지 않아** 미래 예측에 쓸 수 없다. 그래서 입력을 기상 예보가 제공하는 변수로 한정하고, 냄새의 내부 요인은 "분뇨 저장 경과일" 같은 미리 알 수 있는 값으로 대체했다. → 이 원칙이 규칙 1번(서빙 피처 철칙)이 됐다.

**전환 2 — "2주 기다리는 프로젝트"에서 "실데이터 프로젝트"로.** 원래는 익산시 정보공개청구 결과를 기다리며 구조만 만들 계획이었는데, 익산악취24 크롤링으로 \*\*6년 반치 민원 13,039건(시각·좌표·강도 포함)\*\*을 확보하면서 모든 실험이 실데이터로 가능해졌다. 프로젝트의 지위가 "계획"에서 "검증된 시스템"으로 바뀐 분기점.

**전환 3 — 검증 5라운드에서 주장을 시험한 과정.** "기각"이라고 적힌 것들은 실패가 아니라, 심사위원이 물어보기 전에 우리가 먼저 시험해서 주장의 범위를 정확히 잰 결과다:

| 처음 주장 | 시험 결과 | 지금 주장 |
| --- | --- | --- |
| "기상으로 민원을 예측한다" | 성능의 바닥은 달력(계절\+시간대)이었다 | "달력 상식 위에 기상이 **\+4.1%p를 실제로 얹는다**" |
| "특이한 날씨를 잡아낸다" | 증분은 오히려 평범한 날에 컸다 (기각) | "기상의 역할은 극단 상황 탐지가 아니라 **상시적인 미세 보정**" |
| "플룸이 냄새 방향을 맞춘다" | 기준 3개 중 1개만 통과 (근소 미달) | "등급엔 안 쓰고 **참고 정보**로만 — 실좌표 오면 재평가" |
| "전주 관측소면 충분하다" | 익산과 풍향이 절반의 시간 45° 이상 어긋남 | "**바람은 익산(702) 관측소** — 교체로 \+4.6%p 입증" |
| "민원을 줄여준다" | 농가 행동↔민원 데이터가 세상에 없음 | "**상대적으로 위험한 시간대 회피를 돕는다**" |

**그래서 지금의 최종 모습:** 농장주가 아침에 앱을 열면 ① 이번 주 시간대별 민원 위험 캘린더가 자동으로 떠 있고(달력\+기상 결합 모델, 랜덤 대비 2.3배·상위 20% 추천으로 민원 55% 포착), ② 작업 버튼을 누르면 6시간 창 단위 추천과 법령·매뉴얼 근거(RAG 80%)가 카드로 나오고, ③ 작업을 확정하면 영향권 주민 알림 초안이 생성돼 승인 후 발송되는 시스템. 여기에 검증 과정 전체가 기록으로 남아 있어 **"이 숫자를 어디까지 믿어도 되는가"까지 답할 수 있는 것**이 이 프로젝트의 차별점이다.

## 2\. 전체 데이터 흐름 한 장

```
[학습 — 완료됨, 1회]
민원 xlsx ──필터──┐
                  ├─→ 3시간 블록 라벨 테이블(19,208행) ─→ 모델 학습 ─→ model_full.pkl
weather_hourly ───┘        (블록별: 민원 여부 + 그 시각 날씨)

[운영 — 매일 자동]
기상청 예보 API ─→ 저장된 모델 ─→ 7일 위험도 ─→ DB(risk_calendar) ─→ 캘린더 화면

[서비스 레이어]
작업 버튼 ─→ 창(6시간) 단위 추천 + RAG 법령 검색 + 에이전트 카드
작업 확정 ─→ 플룸(익산 바람+농가 좌표) ─→ 알림 대상 주민 + 문구 초안 (승인 후 발송)
```

## 3\. 파이프라인 단계별 상세 (실제 구현 기준)

각 단계마다: **입력(폴더의 어떤 파일) → 처리 → 출력 → 검증에서 확정된 것 → 디벨롭 포인트** 순서다. 스크립트 이름은 demo 폴더 기준.

### 단계 1 — 민원·기상 정제와 라벨 테이블 (etl 계열)

**입력:** 01\_민원데이터 xlsx \+ 02\_기상데이터 weather\_hourly.
**처리:** ① 민원에서 익산시\+가축분뇨만 필터, 같은 좌표 10분 내 중복 신고 제거 → 5,563건 ② 하루를 3시간 블록 8개로 나눈 그리드(2020\~2026.07 \= 19,208블록) 생성 ③ 각 블록에 "민원 있었나(0/1)·몇 건·최대 강도" 라벨 3종 \+ 그 블록의 날씨 평균을 붙임.
**왜 3시간 블록인가:** 신고 시각엔 "냄새 맡고 신고까지"의 지연이 섞여 있어 1시간 단위는 노이즈가 크다. 블록이 이를 흡수한다.
**출력:** label\_table.parquet — 양성률 13.2% (블록 100개 중 13개꼴로 민원 존재).
**주의:** 풍향은 각도 그대로 쓰면 359°와 1°가 정반대로 학습되므로 sin/cos로 변환. 강수량 빈칸은 결측이 아니라 무강수(0) — 기상청 표기 관행.
**디벨롭 포인트(A):** 중복 제거 기준 민감도, 강도 가중 라벨(y\_sev) 활용 실험.

### 단계 2 — 위험도 모델 학습 (train 계열)

**입력:** 라벨 테이블.
**처리:** XGBoost 분류. 피처는 **예보 API가 주는 변수만**(기온·습도·풍속·풍향 sin/cos·강수 \+ 야간×풍속 등 연속 교차항 \+ 블록·월·요일·연도). 분할은 시계열 고정(train \~2024 / valid 2025 / test 2026) — 랜덤 분할은 계절 누수로 금지.
**출력:** model\_full.pkl(단기예보용) \+ model\_reduced.pkl(중기예보용 — 풍향·풍속 없는 축소 피처).
**검증에서 확정된 것:** ① 무풍/고습을 이분법 플래그가 아니라 **연속 변수로 쓰는 버전이 기본 모델** (성능 동급 이상 \+ 예보 오차에 강건) ② 바람 피처는 익산 AWS 사용 ③ 성능 비교는 반드시 같은 월 구성끼리(계절 착시 방지).
**성적:** 주간 랭킹 적중률 0.467 (랜덤 0.20, 달력만 0.427) / PR\-AUC 0.305 / ROC\-AUC 0.711 / 상위 20% 추천 시 실제 민원의 54.9% 포착.
**발표 화법(중요):** "우리 모델 47%"가 아니라 \*\*"달력 상식(0.427) 위에 기상이 \+4.1%p를 실제로 얹는다"\*\*로 말한다 — 자체 검증에서 확정한 프레임.
**디벨롭 포인트(A):** 하이퍼파라미터 튜닝(현재 1차만), 캘리브레이션, SHAP 해석 자료.

### 단계 3 — 운영 배관: 예보→DB→캘린더 (ops 계열)

**입력:** 기상청 단기예보 API(legacy/kma.py — 키 내장, 재사용) \+ 중기예보 API(ops/kma\_mid.py — 구현 완료, 키 넣으면 실전환).
**처리:** 매일 06시 스케줄러(ops/scheduler.py)가 예보 호출 → D\+1\~3은 full 모델(블록 단위), D\+4\~7은 reduced 모델(**일 단위만 — 중기예보에 시간 해상도가 없어서 내린 설계 결정**) → 3등급 변환 → SQLite risk\_calendar 저장.
**출력:** 사용자가 열면 즉시 뜨는 위험도 캘린더 (매번 계산하지 않고 미리 계산해두는 일기예보 앱 방식).
**디벨롭 포인트(B):** 익산 전용 중기기온 구역코드 확정(kma\_mid \-\-probe 준비됨), 실패 알림, PostgreSQL 전환.

### 단계 4 — 작업 창 추천 (scoring 계열)

**입력:** risk\_calendar \+ 작업유형 \+ 농장 설정(분뇨 저장 경과일 등).
**처리:** "시점"이 아니라 \*\*"작업 창"\*\*을 추천 — 작업 시작 후 6시간의 위험도를 감쇠 가중평균(냄새는 시작 순간이 아니라 이후 몇 시간 퍼지므로). 여기에 작업유형 가중치(분뇨제거 1.3 등 — 임의값 \[C\] 명시)와 저장 2주 임계점 보정을 곱해 추천 top\-3 / 회피 top\-3 산출.
**액비 살포만 특별:** 실측 기반 배출량 모델(legacy/emission.py)이 있어 살포량·공법·경운에 따라 가중치가 정량 계산된다.
**디벨롭 포인트(A\+B):** 가중치 \[C\] 값들의 근거 보강, 추천 사유 문구 개선.

### 단계 5 — 플룸: 냄새 방향 계산 (analysis/plume\_multi.py)

**입력:** 축산농가 CSV(주소→좌표 변환 완료본 farm\_coords.csv: 644곳, 그중 돼지 141곳) \+ 익산 AWS 바람 \+ 민원 좌표.
**처리:** 국제 표준 대기확산 모델(Pasquill\-Briggs, legacy 코드 재사용)로 각 농가에서 냄새가 퍼지는 방향·범위를 계산.
**검증 최종 결과(중요):** 검증 기준 3개 중 1개 통과(무작위 대비 1.61배), 2개는 턱밑 미달(이탈각 0.5°, 풍하측 2.4%p 차). 원인은 주소→좌표 변환의 수백 m 오차로 특정됨. **따라서 플룸은 위험 등급에 반영하지 않고(config PLUME\_GRADE\_BUMP\=False) "참고: 풍하측 민가 N동(미검증 모델)" 표시와 주민 알림 대상 선정에만 쓴다.** 허가대장 실좌표를 구하면 plume\_multi 재실행 한 줄로 재평가 — 기준을 넘으면 복원한다.
**디벨롭 포인트(D):** 농가 실좌표 확보(익산시 허가대장), 부채꼴 지도 시각화.

### 단계 6 — RAG: 법령·매뉴얼 Q&A (rag 계열)

**입력:** 03\_RAG\_법령매뉴얼의 PDF들.
**처리:** 법령은 조문 단위, 매뉴얼은 소제목 단위로 잘라(청킹) 한국어 임베딩 모델(**ko\-sroberta — 기본 영어 모델 쓰면 성능 급락, 검증됨**)로 벡터화 → Chroma 저장. 검색 시 질문 유형별로 법령 위계(법률/시행령/시행규칙)를 부스트 — 이 규칙 덕에 77%→**80% 달성**(35문항).
**안전 규칙 2개:** ① "저 고발당하나요?" 같은 개별 판단은 답하지 않고 법률구조공단(132) 안내 ② 가축분뇨법 시행령 별표 1\~9는 **PDF 원문에 내용이 아예 없음이 확인**되어, 해당 질의엔 "원문 미확보 — law.go.kr 확인" 안내가 자동으로 붙는다(DOC 원문 확보 시 교체 스크립트 준비됨).
**디벨롭 포인트(C):** 별표 원문 확보·교체, 평가 문항 확대, 스캔본 매뉴얼 1종 OCR.

### 단계 7 — 에이전트 2종 (agents 계열)

**작업 가이드 에이전트:** Claude API 함수 호출로 도구 6종(캘린더·예보·저장경과일·RAG·농장설정·플룸참고)을 연결, "추천 창 / 대안 / 사전·사후 조치 / 근거(문헌\+익산 실측 인용)" 카드 출력. API 키 없으면 dry\-run 모드로 동작.

**디벨롭 포인트(D):** 시나리오 테스트 확대, 프롬프트 다듬기, 실키 연결.
