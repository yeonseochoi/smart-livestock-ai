# py 파일명 변경 이력

날짜 2026-08-15 · 기준 `main` = `9e8bd48` (PR #6 머지 후)
목적 — **문서 절차번호 기반 이름을 역할이 드러나는 이름으로 교체**

---

## 왜 바꿨나

기존 이름은 계획서의 절차 번호(S0 → S1 → S2 → S3 → S5 → S8)를 파일명에 그대로 박은 것이다.
그 문서를 안 읽은 사람에게는 아무 정보도 주지 않았고, 번호 체계 자체도 이미 깨져 있었다.

```
   s5_recommend.py   s4 는 어디?      → s4 는 파일이 아니라 run_daily 였다
   s8_analysis.py    s6·s7 은?        → s6=rag, s7=agents 인데 파일명엔 흔적 없음
   s2b_spatial.py    s2 와 s2b 관계?   → 계획서를 봐야만 알 수 있었다
```

폴더(`etl/` `model/` `ops/` `scoring/` `analysis/`)가 이미 단계를 나타내므로
파일명에 번호를 중복해 넣을 이유가 없다.

## 명명 원칙

```
   ① 폴더가 단계를 말한다 → 파일명은 '무엇을' 만 말한다
   ② 실행 진입점은 run_ 접두사로 통일
   ③ 버전 구분은 파일명이 아니라 함수명에서 (run() / run_v6())
   ④ 이미 명확한 이름은 건드리지 않는다
   ⑤ 흔한 단어 단독 사용 금지 — 지역변수와 충돌한다
        grid.py  ✗   grid 가 지역변수로 4곳에서 쓰임
        build_grid.py ✓
```

## 산출물 파일명은 이번에 바꾸지 않았다

```
   features_v6.parquet · label_table_v6.parquet · model_{그룹}_full.pkl
   grade_cuts_{그룹}.json · risk_calendar_v6 · forecast_hourly_v6
```

이유
```
   ① v5 산출물(features.parquet)과 v6 산출물(features_v6.parquet)의 구분이 의미 있다.
      두 트랙을 나란히 유지하는 것이 설계 원칙이다.
   ② 바꾸려면 동결 트랙인 v5 쪽도 함께 건드려야 한다.
   ③ 산출물은 커밋되지 않으므로(코드로 재생성) 가독성 이득이 작다.
   ④ DB 테이블명 변경은 마이그레이션이 필요하다.
```

필요하면 별도 단계로 진행한다.
